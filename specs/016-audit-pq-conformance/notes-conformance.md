# PQ Conformance Audit — BC 1.78.1 vs FIPS 203 / FIPS 204

**Date**: 2026-05-20
**Branch**: 016-implement-audit
**Auditor**: spec 016 audit suite (`siida.crypto.audit.*`)
**Subject**: `org.bouncycastle:bcprov-jdk18on:1.78.1`
**Reference**: NIST ACVP-Server vectors (`internalProjection.json`) for
  ML-KEM-keyGen-FIPS203, ML-KEM-encapDecap-FIPS203,
  ML-DSA-keyGen-FIPS204, ML-DSA-sigGen-FIPS204

## TL;DR

| Primitive | Operation | Result | Vectors |
|---|---|---|---|
| ML-KEM-768 | KeyGen      | **FAIL — 0/25 match** | NIST ACVP FIPS 203 |
| ML-KEM-768 | Encapsulate | **PASS — 25/25 match** | NIST ACVP FIPS 203 |
| ML-KEM-768 | Decapsulate | **PASS — 25/25 match** | NIST ACVP FIPS 203 |
| ML-DSA-65  | KeyGen      | **FAIL — 0/25 match** | NIST ACVP FIPS 204 |
| ML-DSA-65  | SigGen      | **FAIL — 0/15 match** | NIST ACVP FIPS 204 tg 3 |

The audit confirms (with the unusual encap/decap nuance) that
BC 1.78.1 ships the NIST **Round-3** Kyber and Dilithium
submissions, not the finalised FIPS 203 / 204 standards. The
finding is the expected one given the timeline:

| Date | Event |
|---|---|
| 2024-04 | BC 1.78.1 released. Contains "Kyber" (Round 3) and "Dilithium" (Round 3) implementations. |
| 2024-08-13 | NIST publishes **FIPS 203** (ML-KEM) and **FIPS 204** (ML-DSA) as final standards. |

## The unusual nuance: ML-KEM encap/decap match FIPS 203

Most "Round 3 vs FIPS 203" gaps are presumed to be byte-for-byte
across the whole primitive. The audit reveals a more nuanced
picture for ML-KEM-768:

- **BC's K-PKE.Encrypt is FIPS 203 conformant.** Given a public
  key generated by a FIPS 203 reference implementation and an
  encapsulation message `m`, BC's `KyberKEMGenerator` produces
  the FIPS 203 expected `(ciphertext, shared_secret)`
  byte-for-byte across all 25 audited vectors.
- **BC's K-PKE.Decrypt + KEM.Decapsulate is FIPS 203
  conformant.** Given a FIPS 203 secret key and ciphertext, BC's
  `KyberKEMExtractor` recovers the FIPS-published shared secret.
- **BC's K-PKE.KeyGen is NOT FIPS 203 conformant.** Given the
  ACVP-published `(d, z)` seeds, BC produces `(ek, dk)` byte
  sequences that diverge from the FIPS 203 reference. This is
  the Round-3 → FIPS 203 keyGen change (likely the `t1` packing
  and PKE-public-key encoding tweaks documented in FIPS 203 §1.4).

**Operational consequences for Siida (spec 012)**:

- Public keys (`HybridPublicBundle`) generated by BC under Siida
  today will NOT interop with FIPS 203 counterparties (e.g.,
  a Siida instance using a future BC version, or any
  third-party ML-KEM-768 implementation).
- BUT, two BC-1.78.1 Siida instances WILL interop with each
  other — keys generated and consumed within the BC 1.78.1
  ecosystem are self-consistent.
- AND, a BC-1.78.1 Siida instance handed a FIPS-203 public key
  by a non-BC peer CAN encrypt to it successfully (encap path
  matches). So one-way encryption from a Siida-1.78.1 client TO
  a FIPS-203 peer works; the reverse direction would need the
  Siida client to publish a FIPS-203-conforming key, which BC
  1.78.1 cannot generate.

This is a real interoperability blocker for any future
multi-implementation deployment, but it does NOT compromise
security or correctness within a single-BC-version deployment.

## ML-DSA-65: comprehensive divergence

For Dilithium, the audit found total mismatch:

- **KeyGen**: 0/25. BC's seed-to-(pk, sk) derivation differs
  from FIPS 204 ML-DSA.KeyGen.
- **SigGen (tg 3, deterministic, pure, external-mu=false)**:
  0/15. Two independent gaps contribute:
  1. **ctx parameter not supported.** FIPS 204's ML-DSA.Sign(sk,
     M, ctx) prepends `0x00 0x00 || ctx || M` to the signing
     input — even when `ctx` is empty. BC 1.78.1's
     `DilithiumSigner` has no `ctx` parameter; it signs `M`
     directly. The audited ACVP tg 3 has non-empty `ctx` in 14
     of 15 cases; even the single empty-ctx case fails because
     the `0x00 0x00` prefix is missing.
  2. **Internal Round-3 vs FIPS 204 differences** in
     ExpandMask, hint encoding, and SHAKE input ordering. These
     would cause divergence even if ctx were handled.

**Operational consequences for Siida (spec 013)**:

- ML-DSA-65 signatures produced by BC 1.78.1 will NOT verify
  against FIPS 204 implementations.
- BC 1.78.1 signatures are self-consistent within the BC
  ecosystem.
- 013's `siida.crypto.api.PqSignature` cannot claim FIPS 204
  conformance with the current BC pin.

## Audit methodology

- Vectors fetched from `github.com/usnistgov/ACVP-Server`
  (`gen-val/json-files/`) under CC0 licence. Committed under
  `modules/crypto/test/resources/acvp/` (down-selected to the
  parameter sets Siida uses: ML-KEM-768 and ML-DSA-65).
- BC's high-level API accepts a `SecureRandom`. The audit
  injects ACVP fixed seeds (`d`, `z`, `m`, `seed`) through a
  `DeterministicSecureRandom` SecureRandom subclass. BC pulls
  bytes via `nextBytes(byte[])` only; injection is transparent.
- Each test case compares BC's outputs against the
  NIST-published expected outputs byte-for-byte.
- The audit lives in `siida.crypto.audit.*` (separate package
  from production crypto code) and runs on every `make test`
  via Mill's default test discovery — no opt-in needed.

## Why the audit suites assert against a baseline (not "all-pass")

If the audit asserted "all 90 vectors must pass" today, the
default `make test` would fail every PR on main until the BC
remediation lands — blocking all other work indefinitely. So
each audit suite asserts the observed pass/fail counts match a
documented baseline:

| Test | Baseline (BC 1.78.1) |
|---|---|
| ML-KEM-768 keyGen | 0/25 |
| ML-KEM-768 encap | 25/25 |
| ML-KEM-768 decap | 25/25 |
| ML-DSA-65 keyGen | 0/25 |
| ML-DSA-65 sigGen tg 3 | 0/15 |

A future BC bump that improves conformance will FLIP the
baseline (e.g., keyGen 0/25 → 25/25), causing the audit suite
to fail with a clear message. The remediation in that case is
to update both the baseline constants in the suite and this
report — an intentional human-in-the-loop checkpoint.

A change in the OPPOSITE direction (BC suddenly worse than
baseline) is also caught: same test failure, same message,
same human-review forcing function.

## Recommended follow-up

A separate spec (**017-bc-version-bump**, not opened in this
PR) should:

1. Bump `bcprov-jdk18on` from 1.78.1 to the latest available
   release that supports FIPS 203 / 204 finalisation (likely
   1.79+ based on BC's release cadence).
2. Re-run the 016 audit suites; expect baseline DRIFT on all
   five tests (most should flip to 25/25 or 15/15).
3. Update the baseline constants in
   `MlKem768ConformanceSuite.scala` and
   `MlDsa65ConformanceSuite.scala`.
4. Update this report with the new BC version's results.
5. If conformance is achieved, **also** update specs 012 / 013 /
   015 to reflect the now-FIPS-conformant primitive choice.

If BC 1.79+ still does not support ML-DSA ctx, the bump should
include either:

- A small Scala-layer wrapper that prepends the FIPS 204
  ctx-prefix before calling BC's `DilithiumSigner`, OR
- A switch from BC's general-purpose provider to
  `org.bouncycastle.tls`'s pqc utilities if those are more
  recent, OR
- A switch to a different PQ provider (liboqs via JNI, AWS-LC,
  etc.) per research R6 — a bigger architectural change.

## bcfips status (verified)

As documented in research R5: `org.bouncycastle:bcfips-jdk18on`
does not yet ship ML-KEM / ML-DSA as of 2026-05. The
general-purpose `bcprov-jdk18on` remains the only BC artefact
exposing these primitives. When `bcfips` adds them (post-CMVP
validation), a separate audit / migration spec will compare.

## What this audit does NOT establish

- **FIPS 140-3 module validation** of Siida or its build. The
  audit covers algorithm-level conformance only; module-level
  CMVP validation is a separate, much larger process (months
  to years) requiring auditor walkthrough and is not in scope.
- **Security analysis** of BC's Round-3 Kyber/Dilithium.
  Cryptanalytically, Round 3 is still considered IND-CCA2
  secure for ML-KEM and EUF-CMA secure for ML-DSA at the same
  parameter sets. The audit's "FAIL" is about
  interoperability, not breakability.
- **Other primitives** introduced by 012 / 013 / 015 (x25519,
  SHA3-256, ChaCha20-Poly1305). Those are well-established
  classical primitives with a long-standing conformance
  history; not part of this audit.

## Sign-off

The audit is mechanically functional. Five test cases run on
every `make test`. Baseline drift on any future BC bump is
caught automatically and forces an explicit human review +
report update before the bump can land. Spec 016 is complete
as a diagnostic instrument.

Remediation (BC bump) is the work of a follow-up spec.

## 2026-05-20 update: remediation landed via spec 017

Spec 017 (BC 1.78.1 → 1.84) closed the gap end-to-end.
Audit results after the bump:

| Test | Before (1.78.1) | After (1.84) |
|---|---|---|
| ML-KEM-768 keyGen | 0/25 | **25/25** ✅ |
| ML-KEM-768 encap | 25/25 | 25/25 ✅ |
| ML-KEM-768 decap | 25/25 | 25/25 ✅ |
| ML-DSA-65 keyGen | 0/25 | **25/25** ✅ |
| ML-DSA-65 sigGen | 0/15 | **15/15** ✅ |

BC 1.84 ships:
- The finalised FIPS 203 ML-KEM-768 (including the corrected
  K-PKE.KeyGen that produces FIPS-published `(ek, dk)` byte-for-byte)
- The finalised FIPS 204 ML-DSA-65 (including ctx parameter
  support via `org.bouncycastle.crypto.params.ParametersWithContext`)

Full bump record — including the BC API class moves from
`pqc.crypto.crystals.*` to `crypto.{generators,kems,signers,params}.*`
— at `specs/017-bc-version-bump/notes-bump.md`.

The audit suite continues running on every `make test` as a
guardrail against future regression.
